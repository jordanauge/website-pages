"Flashing ATtiny Firmware with Arduino as ISP"

2026-05-18 2026-11-09 Electronics #["Arduino" #"ATtiny" #"ISP" #"Firmware"]

Pourquoi une solution personnalisée ?

Utiliser un Arduino comme programmeur ISP (In-System Programmer) pour flasher des microcontrôleurs ATtiny est une pratique courante. Cependant, nous avons rencontré plusieurs limitations et frustrations avec la méthode standard ArduinoISP, en particulier lorsque nous utilisons un ATmega2560 comme programmeur. Pour résoudre ces problèmes, nous avons développé une solution personnalisée basée sur PlatformIO, qui offre plus de contrôle et de flexibilité.

Motivation

L’objectif de ce projet est de rendre la programmation des ATtiny fiable, reproductible et accessible, même avec des cartes programmateur moins courantes comme l’Arduino Mega 2560. Nous voulions une solution qui :

  • fonctionne avec PlatformIO (plus moderne et scriptable que l’IDE Arduino)
  • documente précisément le câblage et les étapes de dépannage
  • permette d’ajouter facilement de nouveaux microcontrôleurs cibles
  • soit open source et maintenable

Le dépôt GitHub : arduino-isp-platformio

Pour les autres cartes (Uno, Nano, Leonardo), voir le README du dépôt.

Remarques importantes

  • Vérifiez que pin 4 (GND) de l’ATtiny est connectée : Sur les petites breadboards sans rail de masse continu, le fil GND doit arriver directement au trou de pin 4, pas seulement quelque part sur la breadboard.
  • Désactiver la réinitialisation automatique : Connectez un condensateur de 10µF entre RESET et GND sur le Mega.
  • ⚠️ Important : Vous devez TEMPORAIREMENT RETIRER ce condensateur lorsque vous flashez le firmware ArduinoISP sur le Mega (il empêche le bootloader auto-reset).
  • Procédure :
    1. Retirez le condensateur 10µF
    2. Flashez le firmware : make upload
    3. Une fois succès, remettez le condensateur en place pour l’utiliser comme programmeur ISP
  • Alimentation stable : Ajoutez un condensateur de découplage (0,1µF) entre VCC et GND sur l’ATtiny.

Pourquoi ce bug persiste ?

Malgré toutes ces précautions, il arrive que certains ATtiny refusent de répondre ou renvoient une signature erronée. Cela peut être dû à :

  • des fusibles configurés pour un oscillateur externe absent
  • une alimentation instable
  • des problèmes de timing SPI

Le problème le plus frustrant : la signature change entre chaque tentative (0x0000ff → 0x00ff00 → 0x000000 → variations aléatoires). Cela indique que l’ATtiny entre bien en mode programmation, mais la communication SPI est instable. Les causes probables incluent des contacts mal serrés sur la breadboard, des désaccords de timing SPI, ou du bruit sur la ligne MISO.

Ce problème reste non résolu malgré :

  • Des connexions correctes (Mega 51/50/52/10 → ATtiny 5/6/7/1)
  • Un condensateur de découplage sur VCC/GND
  • Un condensateur de blocage sur RESET
  • Une horloge externe fournie
  • Des vitesses SPI ralentissies (-B 32, -B 64, -B 128)
  • Une alimentation externe stable

Si vous avez trouvé la solution, toute contribution est la bienvenue sur le GitHub !

  • Dans PlatformIO, ajoutez upload_flags = -B 32 dans votre configuration.

Problème : Bruit ou dérive de tension

  • Ajoutez un condensateur de découplage (0,1µF ou 10µF) entre VCC et GND de l’ATtiny.
  • Assurez-vous que le Mega est alimenté par un port USB fiable.

FAQ

Réglage critique de la vitesse SPI

Le paramètre SPI_CLOCK dans le sketch ArduinoISP est critique et dépend de la vitesse réelle du CPU du chip cible, pas seulement sa fréquence nominale.

Le piège commun : Clock divider par défaut

Par défaut, l’ATtiny85 a un oscillateur interne de 8 MHz, mais également un clock divider de /8 activé dans les fusibles. Cela signifie que la vitesse réelle du CPU est :

8 MHz ÷ 8 = 1 MHz

Exigence SPI : Selon la datasheet AVR, chaque pulse SPI doit être > 2 cycles CPU. Pour un CPU à 1 MHz :

SPI_CLOCK max = 1 MHz ÷ 6 ≈ 167 kHz

Si vous utilisez une vitesse SPI plus rapide (par exemple 250 kHz ou 1 MHz), vous violerez cette exigence et obtiendrez :

  • Signatures invalides qui changent entre les tentatives
  • Erreurs de programmation
  • Comportement imprévisible

Conclusion

Notre outil vise à rendre la programmation ISP des ATtiny simple, robuste et documentée, même pour les cas particuliers comme le Mega 2560. Nous avons documenté les pièges classiques (câblage, alimentation, configuration), et surtout, identifié le facteur critique : la vitesse SPI doit être adaptée à la fréquence réelle du CPU cible, en tenant compte des diviseurs d’horloge des fusibles.

Ce projet apprend une leçon importante pour les makers : toujours consulter la datasheet du chip cible, même pour les settings apparemment “secondaires” comme SPI_CLOCK. Retrouvez tout le code, les exemples de configuration et les instructions détaillées sur GitHub.

Pourquoi utilisons-nous PlatformIO au lieu de l’IDE Arduino ?

PlatformIO offre une meilleure gestion des dépendances, des options de configuration avancées (comme upload_flags), et une intégration facile avec des outils modernes.

Que faire si j’obtiens toujours une signature invalide qui change entre les tentatives ?

C’est presque toujours un problème de vitesse SPI. La signature changeante (0x0000ff → 0x00ff00) indique que le chip ATtiny entre en mode programmation, mais la communication SPI est corrompue par des violations de timing.

Vérifiez la vitesse réelle du CPU :

  • Consultez la datasheet du chip ATtiny cible
  • Tenez compte des fusibles (notamment les clock dividers)
  • Un ATtiny85 avec /8 divider activé par défaut → CPU réel = 1 MHz

Réglez SPI_CLOCK : Dans le sketch ArduinoISP, assurez-vous que :

1
2
// Pour ATtiny85 à 1 MHz réel
SPI.beginTransaction(SPISettings(166667, MSBFIRST, SPI_MODE0));  // 1MHz ÷ 6

Règle générale : SPI_CLOCK doit être au moins 6x plus lent que la fréquence CPU réelle du target.

Puis-je utiliser un autre Arduino comme programmeur ISP ?

Oui, mais les broches SPI et les étapes spécifiques peuvent varier. Consultez la documentation de votre carte Arduino.
