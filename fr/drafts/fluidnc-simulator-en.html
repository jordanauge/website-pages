"fluidnc-sim: a desktop CNC simulator with QEMU firmware emulation and 3D toolpath visualization"

2026-05-12 2026-11-02 CNC
Summary

A desktop simulator that runs the real FluidNC firmware in QEMU and renders the TS35 touchscreen via LVGL on the host, with a live 3D orthographic view of toolpath, hardware plugins, and material removal. Built to develop and test plugins that require visual hardware feedback — touch plate collision, ETS approach sequences, stall detection — without flashing hardware on every iteration.

Prior art

Before building a custom simulator, the obvious options are:

Wokwi is the most accessible ESP32 simulation environment — a browser-based emulator that can run firmware and simulate common peripherals. For simple projects it works well. For FluidNC plugin development, it falls short on two points: there is no support for the SPI TFT + LVGL stack that the TS35 uses, and there is no way to visualize machine state in three dimensions. Wokwi simulates the MCU; it does not simulate a CNC machine. The wokwi-cli command-line variant enables automated testing, but the peripheral limitations remain.

QEMU (Espressif’s ESP32 fork of qemu-system-xtensa) runs real firmware at the instruction level. FluidNC boots, the G-code parser works, the state machine transitions correctly. This is much closer to what we need — but QEMU is headless. It has no display output, no SPI peripheral simulation, and no way to render the TS35 screen. You observe firmware behavior through the serial port, not through the UI.

FluidNC’s native build compiles a subset of FluidNC for Linux/macOS via a PlatformIO native environment. It runs the G-code parser and a few unit tests in isolation. It cannot run plugin code that depends on FreeRTOS or ESP32 peripherals, and has no display or machine state.

What was missing in all three: a way to run the real LVGL display code (the same TS35Display.cpp that runs on the ESP32) on the host desktop, and a way to see machine position in 3D while the firmware runs. The plugins we wanted to build — touch plate collision detection, tool change sequences, stall-triggered feed holds — require visual hardware feedback to develop correctly. That required building the host-side rendering layer ourselves.

Why a desktop simulator

Developing FluidNC plugins means working on two things simultaneously: a ConfigurableModule running on Core 1 (business logic, command generation, state machines) and an LVGL display extension running on Core 0 (UI rendering, touch handling). Both need tight feedback loops.

The standard hardware development cycle — compile, flash (~3 min), boot, test by hand — works for one-off configuration changes. For plugin development it becomes a bottleneck: a session of refining probe sequences, tuning animation timing, or debugging a display layout can involve dozens of iterations. Mistakes are expensive: crashed axes, broken bits, reflashing from a bad state.

fluidnc-sim closes this loop. It runs the real FluidNC firmware in QEMU and renders the real display code on the host desktop. The same TS35Display.cpp compiled for x86/ARM64 instead of Xtensa, the same G-code logic, the same state machines — with a 3D orthographic view of the machine state added on top. Compile, run, see the result in seconds.

Four backends

Backend What runs Use case
QEMU Real FluidNC firmware in Espressif’s ESP32 QEMU fork Full integration testing — firmware + display + plugins
GCodePlayer Host-side G-code interpreter Fast iteration on display/viewer code without building firmware
SerialBridge Physical or wokwi-cli ESP32 via serial/RFC2217 Testing against real hardware from a desktop UI
Renode Renode ESP32 model Alternative emulation path

QEMU mode uses a flash image (flash-qemu.bin) built from the real FluidNC firmware with plugins compiled in. The simulator manages the QEMU process, streams status reports, and routes commands bidirectionally.

PathViewer 3D

The 3D view is an orthographic renderer built on SDL2 RenderDrawLine / RenderFillRect — no GPU shaders. It shows:

  • Toolpath trace: colored by feed rate, with rapid moves dashed
  • Wasteboard and stock: axis-aligned boxes from the YAML config
  • Gantry and spindle: Y rails, X carriage, Z column, motor housings — all rendered as projected boxes
  • Tool: cone frustum matching the current tool diameter from the tool library
  • Hardware plugins: ETS puck, limit switch indicators, StallGuard bar

Controls: left-drag to orbit, right-drag to pan, scroll to zoom, F9–F12 to toggle tool/spindle/gantry/wasteboard visibility.

Hardware simulation plugins

The simulator has a plugin registry for hardware that interacts with the 3D view:

Plugin What it does
ZProbePlugin Renders the ETS puck, detects tool contact, injects [PRB:] results
AutoZeroPlugin Models Sienci AXTP-0002 L-shaped plate with shape-aware tool collision
LimitSwitchPlugin Shows limit switch positions, triggers ALARM:2 on contact
StallGuardPlugin Renders the SG_RESULT bar, simulates stall events
ToolDragPlugin Click-and-drag tool repositioning with mpos sync

Plugins implement ISimHardwarePlugin and self-register via a static macro:

1
REGISTER_SIM_HARDWARE_PLUGIN(viewer3d::ZProbePlugin, z_probe_plugin)

They receive machine state updates every frame, can render overlays in the 3D view, and handle mouse clicks (clicking the ETS puck simulates probe contact).

VoxelCarver

The VoxelCarver is a subtractive material simulation: it maintains a 3D voxel grid representing the stock and removes material as the tool passes through. Each voxel’s removal state is updated based on the tool’s swept volume (cylinder + hemisphere end mill profile).

Two rendering paths:

  • CPU: SDL2 rectangles for each exposed voxel face — works everywhere
  • OpenGL: hardware-accelerated rendering of the voxel mesh — faster for high-resolution grids

Plugin integration

TS35 display extensions (TCH tab, AZ tab, SG tab, Gamepad, Laser Frame) compile into the simulator via the same source files used on the ESP32. The CMake build pulls them in through EXTRA_PLUGIN_DIRS:

cmake -B build \
  -DPLUGIN_SRC_DIR=../fluidnc-ts35display/src \
  -DEXTRA_PLUGIN_DIRS="../fluidnc-toolchange/src;../fluidnc-autozero/src" \
  -DEXTRA_COMPILE_DEFS="USE_TOOL_CHANGE=1;USE_AUTOZERO=1"

Only ts35/*.cpp files from each plugin directory are compiled — the FluidNC ConfigurableModule code runs in the real firmware, not the simulator.

Probe simulation (G38.2 / AutoZero)

The simulator handles G38.2 probing locally — no firmware involvement — with shape-aware collision detection against a virtual touch plate.

  • Adaptive resolution: step count is computed as distance / 0.01mm (clamped 10–5000), so probe precision is always 0.01 mm regardless of travel distance
  • Shape-aware collision: the AutoZero plugin models the Sienci AXTP-0002 L-shaped plate (78×49 mm, 25 mm walls, 5 mm base) and checks contact using the actual tool geometry
  • Tool shape dispatch: V-bit (widening cone), ball-end (hemisphere), endmill (constant cylinder) — each gets correct effective radius at contact height
  • 3D animation: ~50 intermediate waypoints are pushed to PathViewer during probe descent for smooth visual feedback in the 3D view

Clicking the virtual touch plate in the 3D view also triggers an immediate probe contact, useful for quick testing without waiting for the full descent animation.

Laser mode and spindle tracking

The simulator distinguishes CNC and laser configs:

  • M3/M4/M5/S parsing: spindle state (on/off, mode, RPM) is tracked through the entire pipeline
  • Power-mapped trail: PathViewer colors each trail segment by power percentage — blue→yellow→red heat-map when spindle is on, fading green for rapids
  • VoxelCarver laser mode: when the config declares type: Laser, the carver switches from cylindrical endmill sweep to a laser spot with burn depth proportional to S / max_rpm
  • HUD: a bottom-left overlay during Run/Hold shows four bars — feed rate, bit radius, spindle/laser power, and spindle override percentage

The laser fixture (ttc450-laser.yaml) sets type: Laser and max_rpm: 1000, while the CNC fixture uses type: PWM.

Mouse jog (tool drag)

Click on the tool in the 3D view to grab it, then drag to reposition XY. Scroll wheel adjusts Z. The tool is clamped to the machine envelope at all times.

Under the hood, the drag updates both the visual waypoint queue and the SimMachine::mpos[] array synchronously. This dual update ensures the tool stays where you dropped it — no snap-back when the animation queue drains.

Drag action Effect
Left-click tool → drag Move XY within machine envelope
Scroll wheel (while dragging) Adjust Z up/down in 2 mm steps
Release Tool stays at final position

Performance architecture

Three patterns keep the simulator responsive even at high update rates:

  1. Single-lock queue drain: PathViewer acquires its mutex once per frame, swaps the waypoint deque into a local buffer, then processes outside the lock. Writers never contend with the rendering thread beyond one swap.

  2. Atomic empty check: an std::atomic<bool> flag tracks whether the queue has content. The fast path (empty queue, most frames) skips the mutex entirely — zero contention.

  3. Enum-based tool dispatch: AutoZeroPlugin classifies the tool shape into an enum (Endmill | VBit | BallEnd | Drill) once per state change. Collision detection uses a switch instead of per-frame string comparisons.

Combined, these allow the simulator to sustain 60 fps on a MacBook even while streaming thousands of waypoints from a QEMU probe animation.
